# Лабораторная работа 8

## Метрики и анализ ошибок

Методические указания по дисциплине «Проект — применение машинного обучения в креативных технологиях». Магистратура, второй курс, первый семестр курса (третий семестр обучения).

Связь с лекциями: Лекция 4. Компетенции и индикаторы: ПК-1, ПК-1.1.

## Цель

Выбрать систему показателей, которая отражает полезность решения, и получить гипотезу по результатам анализа ошибок.

## Исходная ситуация

Для выдачи референсов важнее получить нужный вариант среди первых результатов, чем угадать все метки. Поэтому для поиска уместны NDCG или MRR, а не только accuracy.

Вход для работы: артефакты предыдущих работ, прежде всего ЛР 7. Результат включается в портфолио и используется на следующих шагах.

## Как читать качество ранжирования

Метрика должна соответствовать действию пользователя. В поиске референсов важно, какие карточки попали в начало списка. NDCG сравнивает полезность фактического порядка с наилучшим порядком тех же оценок релевантности. Recall показывает долю найденных релевантных объектов. Эти показатели не измеряют удобство интерфейса и не подтверждают права на контент.

Среднее может скрывать полный отказ на отдельном сегменте. Поэтому сравнивайте буквальные и синонимические запросы, жанры и сложные случаи. Ошибки данных, разметки, модели и интерфейса имеют разные причины и требуют разных исправлений. Например, неверный genre в карточке нельзя устранить увеличением сложности ранжировщика.

## Развёрнутый порядок выполнения

### Шаг 1 Спецификация метрик

Определите основную метрику, защитные показатели, пороги и правило обработки пустой выдачи. Укажите k и шкалу релевантности. Если у запроса вообще нет релевантных объектов, заранее решите, как он учитывается; не меняйте правило после просмотра результатов.

### Шаг 2 Проверка на одном запросе

Рассчитайте метрику вручную для короткого списка и сопоставьте с кодом. В демо используется gain 2 в степени relevance минус 1; некоторые реализации используют непосредственно relevance. Эти варианты нельзя смешивать при сравнении. Отдельно проверьте пустую выдачу и идеальный порядок.

### Шаг 3 Сегменты

Сгруппируйте запросы по типу и жанру, показывая число наблюдений. Малый сегмент может иметь нестабильное среднее. Не объявляйте один метод универсально лучшим на основании двух запросов одного жанра.

### Шаг 4 Таксономия ошибок

Для каждого типа ошибки запишите наблюдение, частоту с знаменателем, пример, предполагаемую причину и следующий шаг. Не утверждайте причину без проверки. Отдельно отмечайте ошибки, найденные специальными тестами, и ошибки в основной оценочной выборке.

### Шаг 5 Связь с ценностью

Определите недопустимые ошибки: например, выдачу карточки без допуска. Другие ошибки можно временно принять, если пользователь видит ограничение и имеет альтернативу. Свяжите каждое решение с R из ЛР 3 и владельцем риска.

### Шаг 6 Карточка гипотезы

Выберите одно изменение, которое проверяет обнаруженную причину. Укажите ожидаемый эффект, фиксированные условия и критерий отрицательного результата. Не добавляйте одновременно новый индекс, модель и интерфейс: тогда причина изменения качества останется неясной.


## Полный демонстрационный вариант

### Артефакт Спецификация метрик

Единица оценки — запрос. Каталог validation содержит 12 карточек; запросов 12. Релевантность: 2 за нужный жанр и минимализм, 1 за нужный жанр другого стиля, 0 за другой жанр. Главная метрика — средняя NDCG@3. В коде gain равен 2**relevance − 1, дисконт позиции i равен log2(i+1), позиции считаются с единицы.

Пустая выдача получает NDCG и Recall, равные нулю. В данном наборе у каждого запроса есть два релевантных объекта. Для будущих запросов без релевантных объектов необходимо отдельно оценивать корректный отказ; текущая функция возвращает 0 и не интерпретирует такой запрос как качество поиска.

Порог принятия alpha по качеству — 0,70 NDCG@3. Защита: Recall@3 не ниже baseline, неизвестный допуск в выдаче — 0. Продуктовая цель 5 минут до выбора не вычисляется по этой таблице.


### Артефакт Ручной расчёт

Для запроса «джаз минимализм» оценки первых трёх результатов 2, 1, 0. Gain равен 3, 1, 0. Суммарная дисконтированная полезность: 3/1 + 1/log2(3) + 0/2 = 3,63093. Это идеальный порядок, поэтому NDCG@3 = 1. Найдены оба релевантных объекта, Recall@3 = 2/2 = 1.

Если поставить результат уровня 1 перед уровнем 2, полезность равна 1 + 3/log2(3) = 2,89279, а NDCG около 0,797. Пустая выдача имеет 0. Эти случаи проверяются отдельными тестами, чтобы ошибка агрегирования не скрывалась за красивым средним.


### Артефакт Сегменты и ошибки

| Тип | Наблюдение и частота | Пример и причина | Следующий шаг |
|---|---|---|---|
| Неизвестный синоним | 6/12 validation-запросов дают пустую выдачу | «саксофон лаконичный»; слова отсутствуют в train-словаре | Проверить нормализацию терминов |
| Другой язык | 1/1 специального теста no_matches | jazz minimalist; англоязычного словаря нет | Явно обозначить русскоязычную область |
| Неверный ввод | 4/4 негативных модульных проверок отклонены | Пустая строка, 301 символ, null, число | Сохранить явные ошибки контракта |
| Неизвестный допуск | Контрольная карточка скрыта специальным тестом | P003 со статусом unknown | Оставить фильтр перед выдачей |

По каждому из шести жанров имеется два validation-запроса: буквальный с NDCG 1 и синонимический с NDCG 0. Среднее каждого жанра 0,5. Это не шесть независимых подтверждений общей закономерности, а повторение одного шаблона генератора.

Нулевая выдача на английском не входит в 12 основных запросов и не должна менять их знаменатель. Выдача неизвестного допуска недопустима по R3. Пропуск синонима допустим только как явно известное ограничение baseline.


### Артефакт Гипотеза для ЛР 9

H1: замена восьми заранее заданных предметных синонимов каноническими словами перед тем же TF-IDF повысит validation NDCG@3 минимум на 0,10 без снижения Recall@3 и без нарушения фильтра допуска.

Фиксируем данные 1.0, групповой split, IDF из train, k=3, исходные запросы и шкалу релевантности. Изменяем только обработку токенов запроса. Если прирост меньше 0,10 или ухудшена защитная метрика, гипотеза не подтверждена. Проверка полезности для настоящих дизайнеров остаётся отдельной работой.

## Критерии приёмки

Выводы не основаны на одной aggregate-метрике; у ошибок есть примеры и предполагаемая причина; следующий эксперимент связан с наблюдением.

| Критерий | Свидетельство в демо |
|---|---|
| Выводы не основаны на одной aggregate-метрике | Отдельные сегменты и их объёмы |
| у ошибок есть примеры и предполагаемая причина | Таксономия с примерами и проверяемой причиной |
| следующий эксперимент связан с наблюдением | H1 следует из неизвестных токенов |

## Типичные ошибки

Выбор F1 «по привычке»; смешение ошибок модели и ошибок разметки; ручной отбор только красивых примеров; замена анализа списком чисел.
