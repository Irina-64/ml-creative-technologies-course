# Лабораторная работа 11

## Минимальный ML GenAI-модуль

Методические указания по дисциплине «Проект — применение машинного обучения в креативных технологиях». Магистратура, второй курс, первый семестр курса (третий семестр обучения).

Связь с лекциями: Лекция 6. Компетенции и индикаторы: ПК-1, ПК-1.1.

## Цель

Реализовать минимальный рабочий компонент с явным интерфейсом, ограничениями входа и воспроизводимыми настройками.

## Исходная ситуация

Для генератора аннотаций каталога модуль принимает описание экспоната и проверенные записи, формирует черновик и возвращает текст, ссылки на источники и статус, требующий проверки специалистом.

Вход для работы: артефакты предыдущих работ, прежде всего ЛР 10. Результат включается в портфолио и используется на следующих шагах.

## Граница компонента

Минимальный модуль должен принимать понятный вход и возвращать структурированный результат. Контракт описывает типы, обязательные поля, пределы и ошибки. Это позволяет проверять модуль независимо от интерфейса. Для генеративного ассистента дополнительно фиксируются шаблон запроса, источник контекста и правила проверки фактов; выбранный поисковый трек не обязан искусственно добавлять генерацию.

В демо моделью служит статистическое TF-IDF-представление текста, дополненное инженерией знаний. Оценка score выражает сходство векторов, а не вероятность правильности или юридическую допустимость изображения. Это различие необходимо объяснить пользователю и сохранить в документации.

## Развёрнутый порядок выполнения

### Шаг 1 Контракт

Опишите валидный запрос, пустой ввод, неверный тип, превышение длины и структуру результата. Решите, чем отсутствие совпадений отличается от ошибки. Если оба случая возвращают пустой список без статуса, пользователь не сможет выбрать следующий шаг.

### Шаг 2 Сквозная реализация

Соедините чтение каталога, построение модели, поиск и сериализацию ответа без ручного изменения результата. Проверьте один запрос в новом процессе. Ноутбук допустим для исследования, однако сдаваемый модуль должен иметь воспроизводимую точку входа.

### Шаг 3 Конфигурация

Вынесите параметры k, ограничения и версию в отдельный файл. В выбранном локальном варианте секретов нет. Для проекта с API храните ключ отдельно от репозитория и показывайте пример конфигурации без значения секрета. Изменение параметров фиксируйте как новую конфигурацию эксперимента.

### Шаг 4 Набор сложных входов

Проверьте обычный запрос, известный синоним, неизвестный язык, пустую строку, слишком длинный текст и неверный тип. Для генерации добавьте запросы с отсутствующими фактами и конфликтующими инструкциями. Результат теста должен содержать ожидаемое и фактическое поведение.

### Шаг 5 Примеры запуска

Сохраните конкретные запросы и ответы, модель и версию данных. Обрезая большой ответ для отчёта, явно напишите, какие поля опущены; машиночитаемый файл должен оставаться полным. Не заменяйте фактический вывод удобным выдуманным JSON.

### Шаг 6 README и проверка

Напишите установку, команды и ожидаемый результат так, чтобы другой студент запустил модуль без подсказок автора. Укажите рабочую папку, версию Python и отсутствие внешних зависимостей. Проверьте инструкции в отдельном запуске.


## Полный демонстрационный вариант

### Артефакт Контракт

POST /search принимает JSON-объект с полем query типа string. После удаления внешних пробелов допустимы 1–300 символов. Сервер читает тело не больше 4096 байт. Успешный ответ HTTP 200 содержит status, model, results, human_decision_required. Карточка содержит id, genre, style, score, source, rights_status, image.

Статусы: ok — есть совпадения; no_matches — корректный запрос, совпадений нет; fallback — применён резервный поиск. Ошибки HTTP 400: query_must_be_string, empty_query, query_too_long, object_required или ошибка JSON. Неизвестный путь возвращает 404. Score — сходство, не вероятность.

Пример входа:

```json
{"query":"саксофон лаконичный"}
```

Векторизация использует train-IDF 1.0 и lexicon 1.0. Внешняя модель и prompt template не применяются, поскольку это поисковый, а не генеративный трек.


### Артефакт Запускаемый модуль и конфигурация

```powershell
python -m demo.project run
python -m unittest demo.test_project -v
python -m demo.server --port 8765
```

В другом терминале PowerShell:

```powershell
$body = @{query='саксофон лаконичный'} | ConvertTo-Json
$bytes = [Text.Encoding]::UTF8.GetBytes($body)
Invoke-RestMethod -Uri 'http://127.0.0.1:8765/search' -Method Post -ContentType 'application/json; charset=utf-8' -Body $bytes
```

Остановить сервер: Ctrl+C. Полная реализация состоит из demo/project.py и demo/server.py. Конфигурация demo/config.json содержит k=3, max_query_chars=300, model=tfidf+lexicon, model_version=1.0. Все параметры и данные локальны; установка сторонних пакетов для демо не требуется.

| Вход | Ожидаемое поведение | Основание |

| джаз минимализм | 200, ok, карточки | Нормальный сценарий |

## Критерии приёмки

Компонент имеет понятный интерфейс; результаты структурированы; есть обработка неверного ввода; независимый запуск возможен по инструкции.

| Критерий | Свидетельство в демо |
|---|---|
| Компонент имеет понятный интерфейс | Явный контракт и JSON-поля |
| результаты структурированы | Сохранённые фактические ответы |
| есть обработка неверного ввода | Негативные входы и HTTP 400 |
| независимый запуск возможен по инструкции | Полные команды и отсутствие API-ключей |

## Типичные ошибки

Демо только в личной сессии; секрет в коде; свободный текст вместо проверяемого формата ответа; «промпт сработал один раз» вместо тестов.
